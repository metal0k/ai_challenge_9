# Неделя 05 — RAG

День 21: локальный индекс поверх корпуса самого репозитория — chunking,
эмбеддинги, SQLite-хранилище, поиск и сравнение двух стратегий разбиения.
Условие: [`task_05.md`](task_05.md#day-21) (набор документов → chunking →
эмбеддинги → сохранённый индекс, ≥2 стратегии chunking со сравнением).

## Что делает день

1. **Корпус** (`week_05/corpus.py`) — все tracked `*.md` (кроме `.agents/**`)
   плюс `advent_core/*.py` верхнего уровня, прочитанные из коммита
   (`git show <rev>:<path>`), а не из рабочего дерева: незакоммиченная правка
   не должна попасть ни в индекс, ни в кадр демо. Снимок — SHA коммита,
   пишется в `runs.corpus_rev`.
2. **Chunking** (`week_05/chunking.py`) — две честные (намеренно не
   подглядывающие друг в друга) стратегии, `Document -> list[Chunk]`, без сети:
   - `fixed` — скользящее окно 1000 символов, overlap 150, без подгонки к
     границе предложения;
   - `structure` — путь заголовков в Markdown (fence-aware: `#` внутри
     ```` ``` ```` не заголовок) и top-level `def`/`class` в Python через
     `ast`. Секция длиннее 4000 символов режется тем же fixed-окном и
     получает суффикс ` [part i/n]` — инвариант «чанк ≤ 4000 символов» держит
     любая стратегия, включая fallback для непарсящегося файла.
3. **Эмбеддинги** (`advent_core/embeddings.py`) — модель по умолчанию
   `mistral-embed`, батчинг по бюджету символов с адаптивным делением пополам
   на серверный «too many tokens overall», журнал без текста чанков.
4. **Индекс** (`week_05/index.py`) — SQLite (`data/rag/index.sqlite3` по
   умолчанию, `.gitignore`: хранит полный текст чанков), одна транзакция на
   всю пачку запрошенных стратегий — упавшая сеть посреди эмбеддинга не
   оставляет ни полуиндекса, ни смеси старого и нового снимка корпуса.
5. **CLI `adventrag`** (`week_05/cli.py`) — команды ниже.

## Команды

```bash
uv run adventrag index                        # обе стратегии, mistral-embed, HEAD
uv run adventrag index --strategy fixed        # одна стратегия
uv run adventrag index --dry-run               # только chunking + статистика, без API и записи
uv run adventrag compare                       # статистика чанков + качество поиска
uv run adventrag search "как считаются токены" # top-5 по каждой стратегии, 2 строки на результат
uv run adventrag search "вопрос" --strategy fixed -k 3
uv run adventrag show fixed:CLAUDE.md#12       # по chunk_id: метаданные + превью 12 строк
uv run adventrag show week_02/README.md:129    # по файлу и номеру строки
uv run adventrag show CLAUDE.md:253 --full     # полный текст чанка
```

Общий флаг `--db <путь>` есть у всех четырёх команд (по умолчанию
`data/rag/index.sqlite3`). Нет индекса — понятное сообщение «сначала
`adventrag index`», без traceback (`advent_core/errors.py`). Контракт проекта:
таблицы и метаданные — в stdout, прогресс батчей и заметки — в stderr.

## Как устроено сравнение (`compare`)

Две таблицы на stdout:

1. **Статистика чанков и стоимость** — число чанков, распределение размера
   (min/median/p90/max), доля «мелких» (< 200 символов) и доля «разрезов» —
   эвристика, что чанк рвёт содержимое посреди мысли: для Markdown — не
   заканчивается на `.!?:)` или нечётное число открывающих fence-строк; для
   Python — начинается или кончается строго внутри тела top-level `def`/
   `class` (по `ast`-диапазонам всего файла, не фрагмента). Плюс токены
   эмбеддинга, число запросов, время и цена из `runs`.
2. **Качество поиска** — `week_05/eval_questions.json`, 6 вопросов на русском
   с ожидаемым местом ответа (`source` + короткий `anchor`, точная подстрока).
   Попадание засчитывается по тексту чанка (`anchor in chunk.text`), не по
   `section` — иначе сравнение было бы нечестным (у `fixed` секция
   производная). Поиск для метрики всегда top-5; печатаются hit@1, hit@3,
   hit@5 и MRR@5 на каждую стратегию. Вопрос, чей якорь не нашёлся в текущем
   снимке корпуса, — ошибка набора, а не промах стратегии: он исключается из
   метрики и явно перечисляется в stderr.

`compare` (и `search --strategy all`) **отказываются** сравнивать стратегии,
проиндексированные разной моделью эмбеддинга или разным снимком корпуса
(`corpus_rev`) — разные векторные пространства не сравнить, а равный `dim` это
не доказывает. Лидер по MRR@5 печатается только при строгом максимуме; на
ничьей — явная фраза «ничья», а не первый по алфавиту (урок дня 04: `max()`
молча называет победителем первого при равенстве). Рядом с итогом всегда
оговорка: 6 вопросов — малая выборка, разница в одно попадание не значима.

## Day 22 — первый RAG-запрос

Условие: [`task_05.md`](task_05.md#day-22) — вопрос → поиск чанков → объединение
с вопросом → LLM; сравнить ответ без RAG и с RAG на 10 контрольных вопросах.

RAG — это режим **постоянного агента** (`advent_core.agent.Agent`), а не
отдельный скрипт: параметр `rag` (плюс `rag_strategy`, `rag_k`) и команда
`/rag on|off` в `adventagent`. Режимы отличаются одним переключателем.

```bash
uv run adventrag ask "вопрос"            # ответ без RAG и с RAG рядом
uv run adventrag ask "вопрос" --rag      # только с RAG (--no-rag — только без)
uv run adventrag eval                    # 10 контрольных вопросов, таблица и итог
uv run adventrag eval --detail 3         # первые 3 вопроса подробно: ожидаемое и выдержки
uv run adventrag eval --answers          # то же + оба ответа на каждый вопрос
uv run adventagent                       # в REPL: /rag on | off, /rag — состояние
```

Как устроен ход с RAG (`Agent.ask`):

1. Retrieval — первым шагом хода: вопрос эмбеддится той же моделью, которой
   построен индекс (берётся из `runs`, не константа), top-k чанков стратегии
   `structure` (k=5) достаются из SQLite (`week_05/rag.py::make_retriever`).
2. Чанки и вопрос склеиваются в одно user-сообщение
   (`advent_core/rag.py::build_rag_prompt`): инструкция «отвечай по фрагментам,
   нет ответа — скажи прямо, назови источники», пронумерованные фрагменты с
   `source — section`, в конце `Вопрос: …`.
3. В историю пишется **сырой** вопрос: чанки не копятся и не переотправляются
   на следующих ходах. Бюджет (trim, compaction) считается по тому, что реально
   уходит. Контекст ограничен 24 000 символов — лишние чанки отбрасываются, и
   это называется вслух («не вошло»).
4. Сбой retrieval роняет ход, а не превращает его молча в ответ без RAG.

Контрольный набор — `week_05/rag_questions.json`: 10 вопросов, у каждого
`expect` (факты-подстроки с альтернативами: числа и идентификаторы, чтобы язык
ответа не влиял), `sources` (файлы, где ответ есть; альтернативы) и `note`
(ожидание словами). Оценка без LLM-судьи: факт засчитан, если подстрока есть в
ответе (число не засчитывается внутри более длинного числа); источники
считаются раздельно — «попал в top-k» и «назван в ответе». Перед первым
платным вызовом набор сверяется с индексом: факт, которого нет в заявленных
источниках, — ошибка набора, `eval` отказывается стартовать.

Прогон, снятый на видео дня (2026-10-01, `ministral-14b-latest`, индекс на
`e17386c`, `eval --detail 3`, один прогон на ячейку):

| | без RAG | с RAG |
|---|---|---|
| фактов найдено | 2/15 | 7/15 |
| полных ответов | 1/10 | 3/10 |
| токены prompt | 739 | 18 672 (+384 embed) |

Ожидаемый источник в top-5 — 8/10, назван в ответе — 7/10. Память куплена
токенами: prompt вырос в 25 раз. Прогоны без записи давали 1–3/15 против
7–8/15 — разброс одного прогона на ячейку, порядок величин тот же. Два промаха
retrieval: на вопрос 8 ответ есть только в длинном разделе `CLAUDE.md`,
порезанном на 4000-символьные части; на вопрос 7 — в README недели 05, а поиск
поднял код `advent_core/embeddings.py`. Ещё в четырёх вопросах источник найден,
а факта в ответе нет — материал для реранкинга дня 23.

Тесты: `tests/test_rag_core.py`, `test_week05_rag.py`, `test_week05_rag_cli.py`,
плюс RAG-блоки в `test_agent.py`, `test_params.py`, `test_cli_agent.py`,

## Day 23 — реранкинг, фильтрация, query rewrite

Условие: [`task_05.md`](task_05.md#day-23) — второй этап после поиска (reranker
или порог), порог отсечения, top-K до и после фильтра, query rewrite, сравнение
качества без них и с ними.

```bash
uv run adventrag stages                          # ранг релевантного чанка по этапам, без генерации ответов
uv run adventrag stages --threshold 3 --k-before 30
uv run adventrag ask "вопрос" --pair plain,full  # день 22 против rewrite+rerank
uv run adventrag ask "вопрос" --full             # только rewrite+rerank
uv run adventrag eval --pair plain,full --detail 3
uv run adventagent                               # в REPL: /rag full | plain | on | off
```

Режимы: `off` — без RAG, `plain` — день 22 (cosine top-5), `full` —
rewrite + rerank + порог. Параметры агента: `rag_rewrite`, `rag_rerank`,
`rag_k_before` (20), `rag_threshold` (5), `rag_k` (5).

Пайплайн `full` (`week_05/rag.py::make_retriever`, чистые шаги — в
`advent_core/rag.py`):

1. **Query rewrite** — `ministral-14b` переписывает вопрос в поисковый запрос
   (термины, идентификаторы, английские эквиваленты).
2. Исходный вопрос и rewrite эмбеддятся одним вызовом, по каждому — top-20 по
   cosine.
3. **RRF** (reciprocal rank fusion) сливает два списка — без обрезки:
   rewrite в одиночку то помогает, то вредит, слияние гасит провалы.
4. **LLM-rerank** — одна JSON-оценка 0–10 на каждого кандидата (чанки целиком;
   вопрос стоит и до фрагментов, и после).
5. **Порог** — остаются чанки с оценкой ≥ 5, из них top-5 идут в промпт.
   Не прошёл никто — модель получает инструкцию «во фрагментах ответа нет».

Почему порог стоит на оценке reranker'а, а не на cosine: у `mistral-embed`
cosine сжат в полосу 0.73–0.89, медиана релевантных чанков 0.799 против 0.795
у нерелевантных. Даже off-topic не отделяется: top-1 у «борща» 0.779, у
честного вопроса про `cut_static` — 0.772.

Rewrite и rerank — вспомогательные вызовы с изолированными параметрами
(`temperature=0`, свой `max_tokens`, ничего из `.env`); каждый пишет строку в
журнал до разбора ответа.

Dry-run 2026-10-01 (индекс `e17386c`, `structure`, один прогон):

| этап | релевантный в top-5 | на 1-м месте |
|---|---|---|
| cosine (день 22) | 5/10 | 3/10 |
| + rewrite (RRF) | 6/10 | 3/10 |
| + rerank, до порога | 8/10 | 6/10 |
| итог после порога | 8/10 в контексте | 6/10 |

`eval --pair plain,full`, прогон с видео дня: фактов 8/15 → 13/15, полных
ответов 4/10 → 8/10 (на dry-run 7/15 → 9/15 и 3/10 → 6/10 — один прогон на
ячейку, разброс большой, направление одно).
Цена: ~15 тыс. aux-токенов на вопрос (rerank 25–40 целых чанков). Prompt самого
ответа при этом меньше — в контекст попадает 2–4 чанка вместо 5.

Что выяснилось по дороге:

- **Оценки reranker'а бимодальны** — почти всегда 10/8 или 0. Порог между 1 и 9
  почти ничего не решает; разброс между прогонами — шум самого reranker'а.
- **Позиция вопроса в промпте решила больше, чем порог.** Вопрос только после
  40 фрагментов: оценка релевантного чанка на в. 3 — 2/0/0, на в. 8 — 8/3/0.
  Вопрос и до, и после — 7/7/10 и 10/10/10.
- **Rewrite дрейфует.** «Как приготовить борщ?» превратился в запрос про
  pandas-пайплайны; rerank всё равно отсёк всех 40 кандидатов.
- **Пустой контекст ещё не «не знаю».** Когда порог отсёк всё, модель на
  вопросе про `cut_static` проигнорировала «не отвечай по памяти» и выдумала
  фильтр. Это задача дня 24.

Тесты: `tests/test_rag_core.py`, `test_week05_rag.py`, `test_week05_rag_cli.py`,
`test_errors.py`, плюс блоки в `test_agent.py`, `test_params.py`,
`test_cli_agent.py`, `test_record.py`.

## Day 24 — цитаты, источники, «не знаю»

Условие: [`task_05.md`](task_05.md#day-24) — ответ, список источников (source +
section/chunk_id) и цитаты из найденных чанков; проверка на 10 вопросах;
релевантность ниже порога → «не знаю» и просьба уточнить.

```bash
uv run adventrag ask "вопрос" --cite              # ответ + источники + цитаты ✓/✗
uv run adventrag ask "вопрос" --pair full,cite    # день 23 против дня 24
uv run adventrag eval --pair full,cite --detail 2 # 10 вопросов + 3 без ответа в репо
uv run adventagent                                # в REPL: /rag cite
```

Режим `cite` = `full` дня 23 (rewrite + rerank + порог) плюс:

1. **JSON-ответ** `{status, answer, sources:[номера], quotes:[{id, text}]}`.
   Модель называет только номера фрагментов; source, section и chunk_id
   подставляет код — выдумать путь модели нечем.
2. **Цитата проверяется дословно** по тексту фрагмента (сняты только `**`,
   `__`, обратные кавычки и кавычки по краям; `rag_cite` ≠ `ragcite`).
   Цитата, подписанная не тем номером, но дословно найденная в другом
   фрагменте контекста, переатрибутируется кодом: `(модель указала [5])`.
3. **«Не знаю» — правило кода, не просьба к модели:**
   - порог отсёк всех кандидатов → ответ без вызова модели;
   - модель вернула `status: unknown`;
   - ни одна цитата не нашлась дословно → ответ не выдаётся за знание.

   Каждый отказ заканчивается «Уточните вопрос — возможно, вы про: …» —
   секциями ближайших кандидатов. После отказа в REPL следующий ввод ищется
   **как есть**, а предыдущий вопрос видит только rewrite: склейка тащила
   ложную посылку («PostgreSQL») в поиск и снова давала отказ.
4. **Смысл «ответ ↔ цитаты»** в eval оценивает LLM-judge (ministral-14b,
   видит только ответ и дословные цитаты): да / частично / нет. Факты
   считаются по тексту ответа, не по цитатам.

`eval --pair full,cite`, один прогон на ячейку (прогон с видео дня; второй
dry-run — в скобках):

| | RAG+rerank | RAG+цитаты |
|---|---|---|
| фактов из 15 | 12 (12) | 10 (11) |
| источники с дословной цитатой | — | 7/10 (8/10) |
| смысл по judge | — | да 7 (да 7 · частично 1) |
| «не знаю» на отвечаемых | — | 3/10 (2/10) |
| «не знаю» на 3 вопросах без ответа | ≈3/3 (эвристика) | 3/3 (3/3) |

Что выяснилось по дороге:

- **JSON держит цитаты дословнее текста:** 37/39 против 30/37 на пробе; модель
  оборачивает цитаты в `**…**` и «…» — без снятия обёрток дословность 0.
- **Модель сама говорит «не знаю» при непустом контексте — и права:** на
  в. 3 и 8 reranker поставил 10/8 нерелевантным чанкам. Порог — первый рубеж,
  статус модели — второй.
- **Номер фрагмента модель путает чаще, чем текст цитаты.** Дважды верный
  ответ с дословной цитатой превратился в «не знаю»: раз подписан соседним
  номером, раз — `[5]` из заголовка `[part 5/10]` при единственном фрагменте.
- **Строгость стоит фактов:** на первом dry-run 12 → 9 из 15 (три отказа на
  отвечаемых); после переатрибуции — 12 → 11.
- **`full` на вопросах без ответа тоже честен** — «нет информации»; разница
  дня 24 не в отказе как таковом, а в том, что он гарантирован кодом и
  сопровождается уточнением.

Тесты: блоки в `tests/test_rag_core.py`, `test_week05_rag.py`,
`test_week05_rag_cli.py`, `test_agent.py`, `test_cli_agent.py`, `test_params.py`,
`test_record.py`.

## Архитектура: отдельная точка входа

`adventrag` — свой entry point (`week_05.cli:main`), как `adventmcp` у недели
04, а не подкоманда `advent w05`: это CLI поверх локального индекса, а не шаг
существующего агента. Поиск и сравнение — обычные функции модуля
(`week_05/index.py`), не код внутри typer-команды: когда задача попросит
подключить RAG к агенту, появится `week_05/server.py` с MCP-тулом поиска,
читающим тот же SQLite-индекс, и регистрация в реестре серверов — тем же
путём, каким `repo`/`pipeline` уже подключены к агенту недели 04. День 21
такого сервера сознательно не делает.

## Измеренные лимиты (`mistral-embed`, живой замер 2026-09-28)

- Размерность вектора — 1024.
- ≤ 8192 токена на один вход: превышение — 400 `Input id N has X tokens,
  exceeding max 8192 tokens`. Слой эмбеддингов это НЕ лечит перерезкой чанка
  (сломала бы соответствие чанк↔вектор) — ошибка `AdventError` с именем
  чанка-виновника; при кэпе `MAX_CHUNK_CHARS=4000` возникать не должна.
- Суммарно на батч: 47 744 токена проходит, 71 616 — 400 `Too many tokens
  overall, split into more batches.` Точная граница не задокументирована,
  поэтому батчинг делит проблемный диапазон пополам и повторяет, а не
  полагается на константу.
- 60 запросов в минуту (`x-ratelimit-limit-req-minute`).
- Цена `$0.10` за 1M токенов — из сниппета поиска по `mistral.ai/pricing`,
  страница не прочитана целиком; см. комментарий у `PRICE_PER_M_TOKENS` в
  `advent_core/embeddings.py`.
