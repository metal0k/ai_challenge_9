# Неделя 6 — локальный ИИ

День 26: локальная LLM поднята как приватный сервис, запрос идёт по HTTP, три
запроса разной сложности сравниваются с облачной `ministral-14b-latest`.

День 27: постоянный агент `adventagent` (память, RAG с цитатами, MCP) целиком
работает на локальной модели — `adventagent --local`, без облачных вызовов.

Точка входа — `adventlocal` (`week_06/cli.py`), отдельная от `advent`: локальный
сервер — отдельный процесс, а не подкоманда недели.

## Как запустить сервер

Сервер — LM Studio, модель `ornith-1.5-9b` (Q4_K_M, arch qwen35, рассуждающая),
идентификатор `ornith`. Видеокарта RTX 3070 8 GB. Запуск — скриптом из соседнего
проекта `LMStudio_tools`:

```powershell
.\start-local-llm.ps1 -Context 57344
```

Демо модель **не загружает и не перезагружает**: LM Studio общий с другими
сессиями, перезагрузка рвёт их состояние. `adventlocal status` только проверяет
сервер (exit 2 с подсказкой, если модели нет или она не `loaded`).

### Почему контекст 57344, а не 73728

Дефолт скрипта — 73728. С ним на RTX 3070 остаётся свободно 344 MiB VRAM, и
скорость падает с ~53 до 15–20 tok/s: кодовый запрос занял 188 s. С
`-Context 57344` свободно 719 MiB, скорость ~50 tok/s. Это «обрыв» по VRAM:
ухудшение не плавное, а скачком, поэтому демо работает с запасом.

С дня 27 рядом с ornith загружена embedding-модель bge-m3 (635 MB), и запас
съедается снова: при 57344 свободно 309 MiB, генерация 42 tok/s. Поэтому для
дня 27 ornith грузится с `-Context 40960` (свободно 899 MiB) — промпт rerank в
13–20k токенов умещается с запасом.

## Команды

```bash
uv run adventlocal status                 # загруженные модели сервера по HTTP, state, контекст, квантизация
uv run adventlocal status --all           # плюс не загруженные модели
uv run adventlocal status --cli           # плюс `lms ps` (только по явной просьбе)
uv run adventlocal ask "вопрос"           # один запрос: reasoning на stderr, ответ на stdout
echo "вопрос" | uv run adventlocal ask    # вопрос из stdin
uv run adventlocal ask "..." --no-show-thinking
uv run adventlocal compare                # fact, alice, palindrome: локально и в облаке
uv run adventlocal compare --no-cloud     # только локальная модель
uv run adventlocal compare --runs 5 --tasks alice
```

Общие флаги: `--model` (по умолчанию `ornith`), `--url` (или `ADVENT_LOCAL_URL`,
по умолчанию `http://127.0.0.1:1234`), `--max-tokens` (8192: кодовый запрос тратит
до ~3300 токенов на reasoning), `--deadline` (общий предел вызова, 600 s).

- `lms ps` будит headless-сервис LM Studio и сбрасывает его settings.json, поэтому
  `status` его не вызывает, пока не передан `--cli`; ни демо, ни репетиция `--cli`
  не используют.
- Сэмплинг локальной модели — режим «precise» с карточки: temperature 0.6,
  top_p 0.95. Облако получает серверные умолчания (`temperature` не передаётся).
- Persona `default_system.md` не подмешивается ни локально, ни в облаке: она
  гасит reasoning.
- `compare` не зависит от `ADVENT_BASE_URL`: облачная часть всегда ходит в облако.
  Без `MISTRAL_API_KEY` она пропускается с предупреждением.
- Каждый вызов пишется в `logs/calls.jsonl` (`week=6`, `day=26`).

## Задачи и проверки

| id | уровень | проверка |
|---|---|---|
| `fact` | простой | ответ после снятия форматирования — «Канберра» / «Canberra» |
| `alice` | рассуждение | маркер `ОТВЕТ:`, верный ответ 3 |
| `palindrome` | генерация кода | 7 скрытых тестов: 2 латиница, 2 кириллица, 3 негатив |

Всё проверяется кодом, без LLM-судьи. Скрытые тесты называют состав прямо:
кириллица в русском промпте про «знаки препинания» — честная проверка, а не подвох.

## Остаточный риск: исполнение кода модели

Код из ответа модели исполняется в отдельном процессе, но **это не песочница**.
Что сделано: статический отказ до запуска (`ast`: импорт всего, кроме `re`,
`string`, `unicodedata`, `typing`; вызовы `open`/`eval`/`exec`/`compile`/
`__import__`/`input` и др.; атрибуты с `__`) — verdict «небезопасный код, не
исполнялось»; процесс `python -I -S` с окружением из одного `SYSTEMROOT` и `PATH`
(без ключей из `.env`), в пустом временном каталоге; timeout 10 s с `kill`; вывод
ограничен 64 KB. Чего нет: изоляции файловой системы и сети на уровне ОС. Умышленно
обходящий статическую проверку код может навредить — для демо на простой задаче
риск принят.

## День 27 — агент целиком на локальной модели

```bash
uv run adventrag index --local      # локальный индекс на bge-m3 → data/rag/index.local.sqlite3
uv run adventrag compare --local    # hit@k / MRR локального индекса
uv run adventrag check              # индекс локальный и embedding-модель загружена (прогрев JIT)
uv run adventagent --local          # агент на ornith @ 127.0.0.1:1234, облако отключено
```

В REPL: `/local` — сервер, модели, окно и счётчик вызовов «локальных N, облачных
0 (заблокировано K)»; `/set show_thinking off` — спрятать reasoning.

**Как гарантируется «без облака».** `--local` включает offline guard
(`advent_core/offline.py`): каждый HTTP-запрос процесса, включая redirect'ы,
проверяется до отправки, и всё, что не loopback, падает с понятной ошибкой
вместо тихого похода в Mistral или HuggingFace. Локальные клиенты не берут proxy
из окружения. Ключ `MISTRAL_API_KEY` в offline не читается вовсе, на локальный
сервер уходит заглушка; MCP-процессы наследуют offline-режим. Демо записано с
пустым ключом.

**Почему свой HTTP-клиент, а не Mistral SDK.** SDK несовместим с LM Studio в
трёх местах: в streaming не приходит usage, ответ на embeddings падает на
валидации (нет поля `id`), а `response_format: json_object` LM Studio отвергает
с 400. `advent_core/openai_compat.py` говорит с сервером напрямую.

**Embedding-модель.** Сначала был nomic-embed (встроен в LM Studio), но на
русских вопросах к английскому `CLAUDE.md` он почти слеп. bge-m3 мультиязычная:

| | nomic | bge-m3 | облако mistral-embed |
|---|---|---|---|
| structure: hit@5 | 17 % | 67 % | 67 % |
| structure: MRR@5 | 0.167 | 0.556 | 0.347 |

Шесть вопросов — одно попадание не значимо; честный вывод «bge-m3 догнал облако
по hit@5». nomic молча обрезает вход длиннее своего окна (2048 токенов, usage в
ответе = 0), поэтому для него chunk ограничен 1600 символами; bge-m3 реальные
chunk'и до 4000 символов вмещает целиком.

**Rerank на локальной модели.** С reasoning rerank шёл 170 s и в 3 из 10
вопросов обрывался по `max_tokens`. Без reasoning (`reasoning_effort: "none"`) —
быстрее, но ornith писала разбор прозой вместо JSON. Инструкция «только JSON»
этого не лечит; лечит грамматика — `response_format: json_schema`, и тогда
rerank 10/10 за 5–6 s. Ответ с цитатами (`/rag cite`) идёт с той же грамматикой.

Цифры дубля (`0627.mp4`, 2:07): цитаты 4/4 дословны, `JSON ✓`, «локальных 13,
облачных 0 (заблокировано 0)».

## День 28 — RAG целиком локально: сравнение с облаком

Один и тот же RAG-пайплайн (rewrite + rerank + ответ с цитатами, `structure`,
k 5, k_before 20, threshold 5) прогоняется на двух настроенных системах:
облако — `mistral-embed` + `ministral-14b-latest`, локально — `bge-m3` +
`ornith`. Это сравнение систем целиком, а не моделей: протоколы rerank у них
разные (локально — `json_schema`-грамматика и повтор, в облаке — JSON-инструкция),
`temperature`/`top_p` не шлются ни там, ни там, `max_tokens` ответа одинаковый — 4096.

```bash
uv run adventlocal rag                                   # 10 вопросов x 3 прогона x 2 backend'а + 3 вопроса без ответа
uv run adventlocal rag --questions 1,7,9,10 --runs 2 --no-unanswerable   # демо
uv run adventlocal rag --backends local --save local.json
uv run adventlocal rag --report local.json --report cloud.json    # отчёт из сохранённых прогонов, без сети
```

Порядок фиксирован: сначала облако, затем включается offline guard и идёт
локальная фаза; счётчик HTTP (попыток, заблокировано, завершено) печатается
перед таблицами, заблокированный облачный запрос в локальной фазе даёт красную
строку и exit 1. Оба индекса должны быть собраны из одного коммита
(`adventrag index`, `adventrag index --local`), иначе команда отказывается.
Качество считается кодом (факты, цитаты, источник), без judge.

Замер 2026-10-07: оба индекса из коммита `6ee4ac4`, 10 контрольных вопросов и
3 вопроса без ответа в репо, 3 прогона. Backend'ы мерились отдельными запусками
(local — в окно, когда видеокарту не делил эмулятор), отчёт склеен `--report`.

| | облако | локально |
|---|---|---|
| факты | 29/45 | **38/45** |
| вопросов со всеми фактами во всех прогонах | 4/10 | **8/10** |
| ответов, где все цитаты дословны | 18/25 | 20/27 |
| источник в цитатах | **22/24** | 15/26 |
| «не знаю» на отвечаемых | 4/30 | 3/30 |
| неотвечаемые: верный отказ | 9/9 | 9/9 |
| ошибки | 1/39 (rerank — не JSON) | 0/39 |
| все прогоны верны | 7/13 | **11/13** |
| одинаковый вердикт во всех прогонах | 7/13 | **12/13** |
| медиана на вопрос / p90 | **22.6 s / 28.1 s** | 36.4 s / 68.3 s |
| rewrite / rerank / ответ, медианы | 3.9 / 10.3 / 5.1 s | 1.6 / 17.1 / 18.5 s |
| стоимость | $0.13 | $0 |

Выводы:
- **Качество и стабильность — у локальной системы.** Разница держится на
  четырёх вопросах, где облако нестабильно или стабильно ошибается (#6, #7, #8,
  #9); локальная там 3/3. Облачный rerank без грамматики один раз вернул не JSON.
- **Источник в цитатах — у облака**: ornith чаще цитирует фрагмент из файла,
  которого нет среди ожидаемых, хотя факт в ответе верный.
- **Скорость — у облака**, в 1.6× по медиане и вдвое по p90: локальный ответ
  идёт с reasoning (≈30k completion-токенов против ≈5k), rerank — промпт
  ~15k токенов на 8 GB VRAM.
- 3 прогона × 13 вопросов — малая выборка; разница в один-два вопроса не значима.

Вопросы для видео (#1, #7, #9, #10) выбраны **после** замера: два стабильны у
обоих, на двух системы расходятся.

## День 29 — оптимизация локальной модели под задачу

Задача — локальный cite-RAG дня 28 (`bge-m3` + `ornith`). Профиль — полная и
явная конфигурация local-backend'а (`week_06/profiles.py`), и каждый вариант
скрининга меняет ровно один рычаг:

| рычаг | профиль | что меняется |
|---|---|---|
| сэмплинг | `sampling` | t=0.6, top_p=0.95, top_k=20 у ответа (рекомендация карточки ornith для точных задач) |
| max tokens | `cap` | cap ответа 4096 → 1536 |
| reasoning | `noreason` | у ответа выключен reasoning, cite-JSON держит грамматика |
| context window | `ctx24k` | 40960 → 24576 (максимальный промпт — 20.5k) |
| prompt-шаблон | `positional` | rerank отдаёт оценки массивом `[7,0,10,…]` с длиной по грамматике, а не объектами `{"id":…,"score":…}` |
| prompt-шаблон | `k12` | 12 кандидатов в rerank вместо 20 |
| prompt-шаблон | `citelocal` | короткая cite-инструкция под ornith |
| квантование | `q4b` / `q3` / `q5` | Q4_K_M / Q3_K_M / Q5_K_M одной сборки (bartowski, imatrix) |

```bash
uv run adventlocal profiles baseline tuned
uv run adventlocal rag --profile noreason --backends local --runs 1 --no-unanswerable --save noreason.json
uv run adventlocal rag --compare baseline.json noreason.json        # сравнение из сохранённых замеров, без сети
uv run adventlocal rag --compare --tables verdicts baseline.json noreason.json
```

**Защита от путаницы с моделями:**
- Перед замером команда сверяет загруженную модель с профилем: quant, контекст
  и издателя из `/api/v0/models`. Если не совпадает — отказ и подсказка, какую
  модель загрузить.
- VRAM снимается `nvidia-smi` раз в секунду.
- Кванты Q3/Q5 сравниваются с Q4 **той же сборки** (`q4b`), а не с официальным
  Q4. Иначе разница сборок выдавалась бы за разницу квантов.

**Правило выбора записано в спеке до скрининга:**
- Рычаг проходит, если на 10×1 фактов не меньше, чем у baseline − 1, и нет новых
  сбоев. Для контекста и квантов дополнительно нужно свободно ≥ 700 MiB VRAM.
- В `tuned` идут прошедшие рычаги, которые ускоряют ответ.

|---|---|---|---|---|---|
| baseline | 13 | 34.8 s | 21.3 s / 1003 | 7261 MiB | — |

| k12 | 10 | 23.2 s | 12.6 s / 558 | 7261 | ✗ −3 факта; rerank 7.1 s |

### Финал 13×3: до и после

10 контрольных вопросов и 3 вопроса без ответа, по 3 прогона. Профили мерились в
отдельных загрузках модели: baseline при ctx 40960, tuned — при 24576.

| | до (baseline) | после (tuned) |
|---|---|---|
| факты | 38/45 | **39/45** |
| все прогоны верны | 7/10 | **8/10** |
| одинаковый вердикт во всех прогонах | 12/13 | **13/13** |
| неотвечаемые: верный отказ | 9/9 | 9/9 |
| источник в цитатах | 100% | 96% |
| медиана на вопрос | 30.1 s | **20.8 s (−31%)** |
| p90 на вопрос | 60.0 s | **26.7 s (−56%)** |
| ответ, медиана | 16.1 s | **5.9 s (−63%)** |
| completion ответа, медиана | 644 | **221** |
| VRAM пик | 7327 MiB | **6798 MiB (−529)** |

**Вердикт по воротам — «не выполнено», и он оставлен как есть.**
- Из шести ворот не прошло одно: «исправленных источников 1 против 0, не больше
  ×2». Одна цитата пришла с неверным номером фрагмента. Код нашёл её в соседнем
  фрагменте и переатрибутировал, цитата дословная.
- Правило «не больше чем вдвое» при опоре 0 вырождается: провалом становится
  любая единица.
- Правило записано до замера, поэтому после замера его не меняли.

Проверенная цитата доказывает дословность, но не то, что она подтверждает каждое
утверждение ответа. «Без потери качества» здесь значит «без потери по этим
метрикам».

**Выводы:**
- **Главный рычаг — reasoning у ответа.** На этой задаче он не добавлял фактов, а
  стоил ~15 s на вопрос. Без него грамматика `json_schema` удерживает формат
  cite-ответа, а ответ укорачивается в 3–4 раза.
- **Context window — рычаг ресурсов, не скорости.** 24576 вместо 40960 освобождает
  ~0.5 GB VRAM при той же скорости. Это запас до VRAM cliff.
- **Квант меньше ≠ быстрее.** Q3 на 0.8 GB легче Q4, но на этой задаче
  рассуждает дольше: 1104 токена против 664. По времени он проиграл.
- **Q5 не помещается в 8 GB вместе с `bge-m3`.** При 40960 места нет совсем, при
  24576 свободно 342 MiB. Качество было лучшим (13/15), но ценой скорости и
  запаса памяти.
- **Prompt-шаблоны ускоряют rerank, но на 10×1 стоили фактов.** Позиционный
  формат оценок — rerank −30%, сокращённый k — −58%. Различимо ли это с шумом,
  не проверялось, поэтому по правилу их не берём.
- **Cap max_tokens при включённом reasoning вреден.** Модель тратит лимит на
  рассуждение, и ответа не остаётся.
- **Выборка малая.** 10×1 не различает разницу в один факт, 13×3 — в один-два
  вопроса.

Сэмплинг baseline не задавался. Работали дефолты LM Studio: per-model override
для ornith не найден, значения неизвестны. В отчёте `--compare` об этом есть
оговорка.

Вопросы для живого прогона в видео (#1, #7, #9) выбраны после замера: у tuned
они верны во всех трёх прогонах. У baseline #9 был нестабилен.
