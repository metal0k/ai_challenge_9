# Неделя 04 — MCP

День 16: минимальный MCP-клиент. Подключается к серверу по stdio, делает
handshake и печатает список инструментов.

## Запуск

```bash
uv run adventmcp tools                    # собственный сервер репозитория (advent-repo)
uv run adventmcp tools --raw              # + JSON-RPC кадры в stderr (→ клиент, ← сервер)
uv run adventmcp tools --server "python -m my_server" --expect a,b
```

Флаги `tools`:

- `--server "<команда>"` — команда запуска чужого MCP-сервера по stdio
  (пути Windows с пробелами — в кавычках). По умолчанию `python -m week_04.server`.
- Ограничение разбора: `--flag="a b"` (кавычки внутри токена) на Windows не поддерживается — берите значение целиком в кавычки: `"--flag=a b"`.
- `--timeout 15` — секунд на handshake и на каждую страницу `tools/list`.
- `--raw/--no-raw` — зеркалить каждый кадр JSON-RPC в stderr; stdout не меняется.
- `--expect имя,имя` — сверить список с ожидаемым. Для собственного сервера
  по умолчанию ожидаются все его инструменты (`list_days`, `get_task`,
  `count_tokens`, `git_log`, `schedule_job`, `repo_activity_summary`,
  `summarize_text`, `save_to_file`, `commit_digest`), для чужого проверки нет.
  Расхождение — exit 1.

stdout — продукт (таблица инструментов и вердикт сверки); шапка сервера,
raw-кадры и ошибки — в stderr.

## Сервер

`week_04/server.py` — девять инструментов с разными схемами:
`list_days` (без аргументов), `get_task(week, day)` (обязательные int),
`count_tokens(text, model)` (обязательный + опциональный enum),
`git_log(n, query)` (день 17/19, read-only), `schedule_job(interval_seconds)` и
`repo_activity_summary(minutes)` (день 18), `summarize_text(text)`,
`save_to_file(content, filename)` и `commit_digest(query, n)` (день 19,
подробности ниже). В stdout сервер пишет только протокол.

## Ошибки: exit code 8

Любой сбой соединения — `MCPError`, одна строка причины и совет, без traceback:
исполняемый файл не найден; процесс сервера завершился до конца handshake;
сервер пишет в stdout не JSON-RPC; сервер не ответил за `--timeout`; протокольная ошибка. Дочерний процесс
при сбое гасится.

## Демо

```bash
uv run advent record --week 4 --day 16 --dry-run   # прогон без записи
uv run advent record --week 4 --day 16             # запись через OBS
```

Сценарий: успех и сверка → сервер не стартует (exit 8) → сырой лог кадров.

## День 17: git_log

Инструмент `git_log` отдаёт последние коммиты репозитория; агент подключает
сервер через `/mcp on` и вызывает его как обычную function-calling функцию.

## День 18: планировщик и фоновые задачи

Отдельный демон-процесс выполняет job по расписанию, а MCP-тулы только
пишут и читают общий файл состояния `logs/scheduler/repo_activity.json`
(в `.gitignore`). Сам демон MCP-тулы не запускают и не останавливают.

```bash
uv run adventmcp scheduler run                 # демон: цикл, Ctrl+C — остановка
uv run adventmcp scheduler run --interval 15   # + создать/перенастроить job на старте
uv run adventmcp scheduler run --once          # одна проверка и выход, без sleep
```

Демон раз в секунду перечитывает файл, поэтому интервал, изменённый через
`schedule_job`, подхватывается без перезапуска. Весь вывод демона — в stderr,
stdout пуст. Ctrl+C — «прервано» и exit 130.

Инструменты сервера:

- `schedule_job(interval_seconds)` — создать job или сменить интервал
  (5..3600 с; вне границ — ошибка без traceback).
- `repo_activity_summary(minutes=None)` — сводка: число тиков, новые коммиты
  (`N+`, если между тиками их было больше окна сканирования), ошибки тиков,
  последние новые коммиты. Без job'а — ошибка «сначала вызови schedule_job».

Подготовка к демо:

1. Заранее, не в кадре: `uv run adventmcp scheduler run --interval 15`
   в отдельном терминале — к началу записи накопится несколько тиков.
2. В кадре: агент (`/mcp on`) дважды вызывает `repo_activity_summary` с
   паузой между вызовами — число тиков растёт.
3. После записи остановить демон через Ctrl+C, иначе он проработает до
   перезагрузки машины.

## День 19: композиция MCP-инструментов

Один расширенный (`git_log`) и три новых инструмента поверх дней 16–18:

- `git_log(n=5, query=None)` — расширен фильтром: с `query` отдаёт только
  коммиты, чьё сообщение содержит эту подстроку (`git log --grep`, `-i`
  без учёта регистра, `-F` — буквальная подстрока, не regex).
  `query=None` — прежнее поведение дня 17, байт-в-байт.
- `summarize_text(text)` — сжимает произвольный текст в краткую сводку на
  русском. Первый инструмент, который сам делает платный вызов Mistral
  ИЗ ПРОЦЕССА СЕРВЕРА (не агента) — со своим system prompt, персона проекта
  не подмешивается. Вызов уходит в тот же JSONL-журнал, что и вызовы агента.
- `save_to_file(content, filename)` — пишет текст под `logs/pipeline/`
  (уже в `.gitignore`). `filename` — только имя файла, без подкаталогов и
  без `..`.
- `commit_digest(query, n=20)` — composed-тул: находит коммиты по `query`,
  сжимает их сводкой и сохраняет результат в файл — всё внутри ОДНОГО
  вызова инструмента. Если совпадений нет, `summarize_text` и `save_to_file`
  не вызываются вовсе — короткое замыкание на пустом результате поиска, а
  не сводка по пустоте и не бессмысленный файл.

**Почему composed-тул, а не три раунда function-calling.** В чате курса
на вопрос, нужно ли собирать цепочку search → summarize → saveToFile через
несколько раундов у агента, прозвучало «да да тут в рамках одного mcp-tool».
У этого решения есть и независимая техническая причина: клиент этого
проекта (`advent_core/mcp_client.py::call_tool_once`) поднимает
короткоживущий подпроцесс на каждый вызов инструмента — три раунда
означали бы три запуска процесса `week_04.server` (три `load_dotenv`, три
handshake) вместо одного. `commit_digest` вызывает `summarize_text` и
`save_to_file` как обычные Python-функции внутри одного процесса — дешевле
в разы, а не только «правильный ответ на вопрос из чата».

## День 20: оркестрация нескольких MCP-серверов

Агент получает инструменты сразу с трёх серверов, сам выбирает нужный и
проходит длинный флоу: `repo` → `pipeline` → внешний `fs`.

| сервер | что это | инструменты для модели |
|---|---|---|
| `repo` | фасад над `week_04/server.py` (`servers_repo.py`) | `list_days`, `get_task`, `git_log`, `count_tokens` |
| `pipeline` | фасад (`servers_pipeline.py`) | `summarize_text` (`commit_digest` отфильтрован allow-списком) |
| `fs` | `@modelcontextprotocol/server-filesystem@2026.8.31` через `npx`, замкнут на `logs/pipeline/` | `list_allowed_directories`, `write_file`, `read_text_file`, `list_directory` |

Фасады импортируют функции из `server.py` и регистрируют их на своём сервере
(`@mcp.tool` возвращает функцию как есть), логика не дублируется; сам
`server.py` дней 16-19 не тронут.

### Реестр и router

- `week_04/servers.json` — список `{name, command, args, cwd?, allow?, timeout?,
  ensure_dirs?}`. Пути не хранятся: `{repo}` и `{python}` разворачиваются кодом,
  на Windows `npx` превращается в `npx.cmd`. Версия пакета `fs` закреплена.
- `advent_core/mcp_router.py` собирает `tools/list` со всех серверов, отдаёт модели
  имена `сервер__инструмент` (алфавит `A-Za-z0-9_-`, до 64 символов; более длинные
  имена сокращаются детерминированно с хэшем), режет allow-списком и
  диспетчеризует вызов нужному серверу. Как и `Agent.call_tool`, `Router.call`
  никогда не бросает: неизвестное имя или упавший сервер приходят модели текстом
  ошибки со списком допустимых имён.
- Недоступный сервер при `/mcp on` — предупреждение с причиной; остальные работают.
- Спавн остаётся per-call, как в днях 16-17. Холодный `npx -y` — около 22 с, тёплый —
  около 2 с; `advent record` прогревает кэш перед записью. stderr дочернего
  процесса `fs` (баннер) для серверов реестра подавляется.
- Трасса: строка в stderr на каждый вызов (`раунд N · сервер → инструмент (байты, сек)`),
  таблица «Маршрут хода» в конце хода, строка `kind=mcp_route` в JSONL-журнале.
- `tools=` невидим локальному счётчику токенов, поэтому сверка с сервером в этом
  режиме пропускается; после хода печатается `prompt_tokens` раунда 1 (со схемами).
- Лимит раундов — параметр `Agent.max_tool_rounds` (3 по умолчанию, 8 в режиме
  реестра); меняется `/mcp rounds N` и `/mcp rounds default`, хранится в файле
  сессии ключом `mcp_max_rounds` (аддитивно, `SESSION_VERSION` не менялся).

Если `week_04/servers.json` нет, `/mcp on` работает как в днях 17-19.
