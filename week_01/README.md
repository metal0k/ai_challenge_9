# Неделя 01

Код всей недели лежит в этой папке; условия дней — разделы `## Day NN` в
[`tasks.md`](tasks.md) рядом. Приложение растёт по дням, состояние каждого
сданного дня зафиксировано тегом.

## Day 01 — первый запрос к LLM через API

**Условие:** [`tasks.md`](tasks.md#day-01) — минимальный код, который отправляет
запрос в LLM через API, получает ответ и выводит его в CLI.
**Тег:** [`w01d01`](https://github.com/metal0k/ai_challenge_9/tree/w01d01)

### Что сделано

- Запрос в Mistral через официальный SDK, **streaming** — токены печатаются по
  мере генерации.
- Два режима: one-shot (`advent w01 chat "вопрос"`) и REPL с историей диалога.
- Выбор модели и её настроек: `/model list`, `/model info`, `/params`, `/set`.
- Телеметрия после ответа: реальная версия модели, latency, токены.
- Понятные ошибки вместо traceback: нет ключа, неверный ключ, лимит, таймаут.
- Все вызовы пишутся в `logs/calls.jsonl` — пригодится в поздних заданиях.

### Команды

| Команда | Что делает |
|---------|-----------|
| `advent w01 chat [вопрос]` | Вопрос модели; без аргумента — REPL |
| `advent w01 models` | Список моделей из API (`--all` — включая не-chat) |

Флаги `chat`: `--model`, `--system`, `--temperature`, `--top-p`, `--max-tokens`,
`--seed`, `--stop`, `--reasoning-effort`, `--no-stream`, `--verbose`.

Команды REPL: `/help`, `/model`, `/model <имя>`, `/model list`, `/model info`,
`/params`, `/set <параметр> <значение>`, `/reset`, `/exit`.

### Демо-сценарий

Фиксированный: модель каждый раз отвечает по-разному, а порядок шагов — нет.
Прогоняется одной командой `uv run advent record --day 1` (или `--dry-run`,
чтобы посмотреть без записи).

**1. Какие модели доступны аккаунту**

```bash
uv run advent w01 models
```

Список приходит из живого `GET /v1/models`, а не зашит в код. Внизу видно, во
что разрешается алиас: `mistral-small-latest сейчас разрешается в mistral-small-2603`.

**2. Один вопрос — ответ стримится**

```bash
uv run advent w01 chat "Объясни в двух предложениях, что такое LLM"
```

Ответ печатается по мере генерации, в конце — футер:
`· model mistral-small-latest → mistral-small-2603 · 2480 ms · tokens 73/76/149`

**3. Диалог с историей**

- `Назови три языка программирования для бэкенда`
- `А какой из них быстрее всего учить?` — второй вопрос опирается на первый,
  модель помнит контекст
- `/reset`, `/exit`

**4. Настройки модели**

`/model info` → `/params` → `/set temperature 0` → `/set reasoning_effort high`
→ вопрос → `/model codestral-latest`. На последнем шаге видно, как параметр,
которого у модели нет, отсеивается с предупреждением.

**5. Неверный ключ — аккуратная ошибка**

```bash
MISTRAL_API_KEY=invalid uv run advent w01 chat "привет"
```

```
Ошибка: Ключ Mistral отклонён (401).
Проверь MISTRAL_API_KEY в .env — возможно, ключ отозван или скопирован не полностью.
```

Exit code 3, никакого traceback.

## Day 02 — формат ответа

**Условие:** [`tasks.md`](tasks.md#day-02) — тот же запрос, но с явным
описанием формата ответа, ограничением длины и условием завершения; сравнить
ответ без ограничений и с ограничениями.
**Спека:** [`specs/SPEC-w01d02.md`](../specs/SPEC-w01d02.md) (не в репозитории
— `specs/` в `.gitignore`).
**Тег:** [`w01d02`](https://github.com/metal0k/ai_challenge_9/tree/w01d02)

### Что сделано

- **Пять новых параметров**, все — переключалки, а не зашитая лесенка:
  `format` (`text`/`json`/`schema`/`yaml`/`md`), `schema_file`, `done`, `mode`
  (`chat`/`dialog`), `max_turns`. Задаются флагом CLI или `/set`, на сервер не
  уходят (`Spec.local=True`) — `as_payload()` их молча пропускает.
- **Формат ответа = промпт + `response_format`.** Для `json`/`schema` уходит и
  инструкция в system, и параметр API; доки Mistral прямо требуют инструкцию
  даже с параметром выставленным. Для `yaml`/`md` API-опоры нет вовсе — только
  промпт, и это главный контраст дня.
- **Схема** — файл (`week_01/schemas/*.json`), `/set schema_file <путь>`,
  валидируется по-настоящему через `jsonschema.validate`, не сверкой ключей.
- **`finish_reason` виден в footer** и отличает «модель закончила сама»
  (`stop`) от «упёрлась в `max_tokens`» (`length`), рядом — вердикт по формату
  (`JSON ✓ · схема ✓ · items: 3`, или `—` для `yaml`/`md`, где вердикта нет).
- **`/again`** — повторить последний вопрос с текущими настройками без
  истории. Это и есть «один и тот же запрос» из задания, и защита от того,
  что модель начнёт «как я говорил выше» при обычном повторе через историю.
- **`mode=dialog`** — короткий диалог до готовности (сценарий «хочу
  приготовить салат» из заметок автора курса): модель задаёт по одному
  уточняющему вопросу за ход, `done` определяет признак завершения
  (`text:<строка>` — подстрока, `json:<поле>` — булево поле), `max_turns`
  не даёт разговору зависнуть.
- **Ловушка с `stop`**: маркер завершения нельзя передавать через параметр
  `stop` — API вырезает стоп-строку из вывода («The output will not contain
  the stop sequence»), и детектировать её в ответе становится нечем. Шаг 6
  демо показывает это намеренно, как Day 01 показывал неверный ключ.
- **Отказ модели на `response_format`** — ни у одной из 48 моделей аккаунта
  нет отдельной capability для structured output, поэтому параметр уходит
  всегда, а 400 от API переводится в понятное сообщение, не в traceback.

### Новые команды и параметры

Флаги `chat`, добавленные к списку Day 01: `--format`, `--schema-file`,
`--done`, `--mode`, `--max-turns`.

| Параметр | Значения | Смысл |
|----------|----------|-------|
| `format` | `text` `json` `schema` `yaml` `md` | Пресет формата ответа |
| `schema_file` | путь к `.json` | Схема для `format=schema` |
| `done` | `text:<строка>` / `json:<поле>` | Условие завершения диалога |
| `mode` | `chat` `dialog` | Обычный REPL или диалог до готовности |
| `max_turns` | целое, по умолчанию 10 | Потолок ходов в `mode=dialog` |

Новая команда REPL: **`/again`** — повторить последний вопрос с текущими
настройками, без истории (недоступна в `mode=dialog`, где история — суть
диалога). `/set` и `/params` работают с новыми параметрами так же, как и со
старыми; `/params` дополнительно показывает итоговый system prompt целиком —
то, что реально уйдёт в API, с дописанной инструкцией формата.

### Демо-сценарий

Сквозной вопрос: **«Назови 3 ингредиента для греческого салата с
количеством»** — ложится и в `items[{name, amount}]` (json/schema), и в
таблицу Markdown, и в YAML-список, и связан с диалогом про салат.
Прогоняется командой `uv run advent record --day 2` (или `--dry-run`).

**1. Тот же вопрос без ограничений** — базовая линия: длинный свободный текст.

**2. `format` json → schema → yaml → md** через `/set format …` и `/again` —
видно, как одна и та же переключалка меняет форму ответа; у `yaml`/`md`
вердикта в footer нет.

**3. `/again` ×3 при `format=schema`** — структура ответа (`items[{name,
amount}]`) одинакова во всех трёх прогонах, несмотря на то что текст каждый
раз генерируется заново.

**4а. `max_tokens 20`** — ответ обрывается посреди фразы, `finish=length`.
Порог именно 20: в 40 токенов модель укладывает ответ про салат целиком и
завершает сама, и шаг перестаёт показывать то, ради чего он есть.
**4б. Инструкция «не более 3 предложений»** (`--system
week_01/prompts/brief_system.md`) — модель останавливается сама, `finish=stop`.
Оба шага на `format=text`, чтобы не смешивать урок про длину с уроком про формат.

**5. `mode=dialog`, `done=json:done`** — «Хочу приготовить салат» → модель
уточняет вид, ингредиенты, порции → возвращает готовый результат с признаком
завершения; счётчик ходов виден в сообщении.

**6. `stop` с тем же маркером, что просит вывести system prompt** — ловушка:
API вырезает стоп-строку, детектировать в ответе нечего. Показывает, что
параметры реально уходят на сервер, а не только в промпт.

**7а. `format=json` с `max_tokens 25`** — JSON рвётся на полуслове,
`finish=length ⚠ · JSON ✗ обрыв`. Шаг доказывает, что вердикт формата
настоящий, а не печатает «✓» при любом ответе.

**7б. `format=schema` без `schema_file`** — понятная ошибка вместо traceback.

Исходно шагом 7 планировался отказ модели, не умеющей structured output. От него
пришлось отказаться: на этом аккаунте отказа добиться нечем. Проверены
`codestral`, `ministral-3b`, `voxtral`, `mistral-code-fim`, `magistral-medium` —
**все 29 chat-моделей принимают `json_schema`**, и у всех 29 стоит
`function_calling: true`. Побочный вывод важнее самого шага: гейтить
`response_format` по этому флагу было бы бессмысленно, потому что он не
отсеивает ни одной модели.

## Day 03 — разные способы рассуждения

**Условие:** [`tasks.md`](tasks.md#day-03) — одну задачу решить четырьмя
способами (прямой ответ, «решай пошагово», промпт, написанный самой моделью,
группа экспертов) и сравнить: расходятся ли ответы и какой способ точнее.
**Спека:** [`specs/SPEC-w01d03.md`](../specs/SPEC-w01d03.md) (не в репозитории
— `specs/` в `.gitignore`).
**Тег:** [`w01d03`](https://github.com/metal0k/ai_challenge_9/tree/w01d03)

### Что сделано

- **Четыре способа рассуждения** в `week_01/strategies.py`, промпты вынесены в
  `week_01/prompts/reason_*.md` и правятся без правки кода:

  | Способ | Вызовов | Что делает |
  |--------|---------|------------|
  | `direct` | 1 | задача как есть, без единой добавки |
  | `steps` | 1 | в system добавлена инструкция рассуждать пошагово |
  | `meta` | 2 | модель сначала пишет **промпт для решения**, потом решает по нему |
  | `panel` | 4 | аналитик, инженер и критик решают независимо, четвёртый вызов сводит |

- **Новая команда `advent w01 solve`** — прогнать задачу всеми способами и
  напечатать таблицу сравнения. Та же механика доступна из чата:
  `chat --strategy panel "…"` и `/set strategy panel` в REPL.
- **Банк задач** `week_01/problems/*.json`: условие, эталон, синонимы
  правильного ответа (`accept`) и `note` — чем задача хороша. Задача дня
  помечена `"default": true`.
- **Извлечение ответа маркером `ОТВЕТ:`** — одинаковая добавка ко всем четырём
  способам, поэтому никому не даёт форы. Берётся **последнее** вхождение:
  модель по дороге упоминает требуемый формат. Сверка нормализует регистр,
  пробелы, концевую точку и `ё` → `е`. Отсутствие маркера — отдельный вердикт
  «маркер не найден», а не тихий минус: не извлекли и ответили неверно — разные
  вещи.
- **LLM-судья** — один вызов на все четыре ответа, `json_schema` из Day 02
  (`week_01/schemas/judge.json`). Ответы поданы под метками A–D **без названий
  способов** (иначе «группа экспертов» получает фору просто из-за названия) и
  **без эталона**: судья оценивает рассуждение, а не совпадение с ключом.
- **Учёт стоимости способа**: `advent_core/telemetry.py` научился складывать
  несколько вызовов в один `Totals` (вызовы, токены, время). Панель дороже
  прямого ответа вчетверо — это видно цифрой в таблице, а не на словах.
- **Журнал** `logs/calls.jsonl` помечает каждую строку `strategy` / `step` /
  `problem` / `run`, вызов судьи — `strategy=judge`. Единица записи — **один
  вызов**: строка уходит в файл сразу после успешного ответа API, а не когда
  стратегия дойдёт до конца. Поэтому 429 на четвёртом вызове панели не уносит
  с собой три уже оплаченных — они и на экране, и в журнале. Таблица сравнения
  при таком обрыве не печатается: она сводит то, чего не досчитали.

### Команды и параметры

```bash
uv run advent w01 solve                                  # все четыре способа + судья
uv run advent w01 solve --strategy panel --no-judge
uv run advent w01 solve --problem nines --strategy direct --runs 3
uv run advent w01 chat --strategy steps "…"              # то же из чата
```

| Параметр | Значения | По умолчанию |
|----------|----------|--------------|
| `strategy` | `direct` `steps` `meta` `panel` `all` | `direct` в `chat`, `all` в `solve` |
| `problem` | id задачи из `problems/` | помеченная `"default": true` |
| `runs` | целое ≥ 1 | 1 |
| `judge` | вкл/выкл | вкл в `solve`, выкл в `chat` |
| `judge_model` | имя модели | та же, что решала |

Все пять — локальные (`Spec.local=True`), на сервер не уходят. Задаются флагом
CLI или `/set`; переменных окружения у них нет — `Config.resolve()` читает из
`.env` только генерационные параметры и `ADVENT_SYSTEM_PROMPT`. Опечатка в
`--problem` и недоступная `--judge-model` останавливают команду **до** первого
обращения к API, а не после девяти оплаченных вызовов.

### Что показывает таблица

Форма вывода фиксирована, числа зависят от прогона:

```
                  Сёстры брата Алисы · эталон: 3
┌───────────┬────────┬────────┬───────────┬─────────┬─────────┬────────┐
│ стратегия │ ответ  │ эталон │  судья    │ вызовов │  токены │  время │
├───────────┼────────┼────────┼───────────┼─────────┼─────────┼────────┤
│ direct    │ 2      │   ✗    │ #4 · 4/10 │       1 │ 118/96  │  1.6 s │
│ steps     │ 3      │   ✓    │ #2 · 8/10 │       1 │ 131/402 │  5.9 s │
│ meta      │ 3      │   ✓    │ #1 · 9/10 │       2 │ 268/691 │ 11.4 s │
│ panel     │ 3      │   ✓    │ #3 · 7/10 │       4 │ 612/903 │ 18.2 s │
└───────────┴────────┴────────┴───────────┴─────────┴─────────┴────────┘
```

- **ответ** — то, что стояло после `ОТВЕТ:`; **эталон** — детерминированная
  сверка с ключом задачи (при `--runs N` здесь `k/N`);
- **судья** — место в ранжировании и балл; ниже таблицы печатаются его
  комментарии;
- **токены** — `prompt/completion`, **вызовов** — цена способа.

Расхождение судьи с эталоном — **результат дня, а не сбой**: он эталона не
видит и оценивает качество рассуждения. Когда его первое место по ключу
неверно, это сказано отдельной строкой. Известное ограничение: порядок ответов
A–D фиксирован, позиционная предвзятость судьи не компенсируется.

### Демо-сценарий

Прогоняется командой `uv run advent record --day 3` (или `--dry-run`). Задача —
`alice`, та же во всех шагах; условие для шага 2 берётся из файла банка, а не
из копии в коде.

**1. Задача, эталон и прямой ответ ×3** (`solve --strategy direct --runs 3
--no-judge`) — условие и ключ печатаются перед первым вызовом. Три прогона, а не
один: прямой ответ верен 1 раз из 5, но на одном броске он может угадать и
увести посылку дня в никуда. Колонка эталона показывает `k/3`.

**2. `chat --strategy steps "…"`** — вторая поверхность: та же машинерия из
обычного чата. Пошаговое рассуждение доходит до 3.

**3. `solve --strategy meta`** — видно самое интересное в способе: промпт,
который модель написала себе сама, печатается целиком.

**4. `solve --strategy panel`** — три эксперта решают, не видя друг друга, и
синтез сводит их ответы.

**5. `solve` целиком** — четыре способа подряд, судья и таблица. Шаг повторяет
вызовы шагов 1–4: если запись не укладывается по времени, сокращать надо
промежуточные шаги, а не его — таблица и есть итог дня.

### Подбор задачи: что выяснилось

Задачу нельзя взять из головы — способы расходятся не на любой. Перебрано 18
кандидатов по 4 прогона на `mistral-small-latest`:

- **Классические загадки-подвохи бесполезны** («пятая дочь», «пять станков за
  пять минут», подсчёт букв в слове) — решаются 4 из 4. Они есть в обучающих
  данных, и модель их вспоминает, а не решает.
- **Длинные арифметические цепочки тоже** — считает лучше, чем ожидалось.
- Устойчивый промах дал ровно один класс: **счёт отношений, где считающий не
  включает себя**.
- Внутри этого класса задачу пришлось менять ещё раз, уже на готовом конвейере.
  `children` (ответ 7) даёт промах, но одинаковый: по 5 прогонов пошаговое
  рассуждение верно 2 раза из 5 — ровно столько же, сколько прямой ответ, то
  есть сравнивать нечего. Задача дня — `alice` (ответ 3, «сколько сестёр у
  брата Алисы»): **1 из 10 прямым ответом против 10 из 10 пошагово**. **Задачу
  мало выбрать по классу — разрыв надо измерить на той же связке, которая
  поедет в кадре.**
- **Пять прогонов не отличают 50% от 80%.** Первый замер дал пошаговому 4 из 5,
  десять прогонов того же промпта — 5 из 10.
- **Сильнее всего на результат повлияла формулировка самой инструкции**
  «решай пошагово». По 10 прогонов на `alice`: без инструкции 0 из 10;
  с нумерованными правилами, заканчивающимися «проверь результат
  подстановкой», — 5 из 10; с короткой алгебраической формулировкой «разбери
  условие, введи обозначения, выпиши уравнения» — 9 из 10. Вредным оказалось
  именно правило самопроверки: модель перевыводила счёт сестёр не с той точки
  зрения и переубеждала себя. Четвёртый вариант тоже дал 9 из 10, но за счёт
  подсказки «посмотри, с чьей точки зрения задан вопрос», заточенной под эту
  задачу, — и потому отклонён: промпт, подогнанный под задачу замера, измеряет
  подгонку, а не стратегию.
- **Два эталона из собственной головы оказались неверными** — в задаче про
  носки и в задаче про поезда модель была права, а ключ нет. Эталон в банке —
  такой же объект проверки, как и ответ модели.
- `digits5` оставлена в банке намеренно как контрпример: там все четыре способа
  верны, и панель — это вчетверо больше токенов ради того же ответа.

## Day 04 — температура

**Условие:** [`tasks.md`](tasks.md#day-04) — один и тот же запрос при
`temperature` 0, 0.7, 1.2; сравнить ответы по точности, креативности и
разнообразию и сформулировать, для каких задач подходит каждая настройка.
**Спека:** [`specs/SPEC-w01d04.md`](../specs/SPEC-w01d04.md) (не в репозитории
— `specs/` в `.gitignore`).
**Тег:** `w01d04` (после сдачи).

### Что сделано

- **Новая команда `advent w01 temp`** — та же задача прогоняется на всех
  заданных температурах, N раз каждая, с таблицей метрик на выходе.
- **Три задачи в развёртке, и состав — это и есть вывод дня**: `digits5`
  (модель решает верно), `alice` (модель систематически ошибается) и `coffee`
  (эталона нет по определению — название кофейни). Первые две дают
  противоположные ответы на вопрос «какая температура точнее», и только пара
  показывает, почему сам вопрос некорректен.
- **Метрики считаются кодом, не на глаз**: точность — сверка с эталоном
  (у `digits5` и `alice`), соблюдение формата — `k/N`, разнообразие — число
  различных **нормализованных** ответов из N (иначе `"Морская волна"` и
  `" Морская волна"` считаются двумя разными ответами вместо одного).
  Креативность — не машинная метрика: на open-задаче (`coffee`) команда
  печатает все ответы каждой температуры рядом (блок «оценка креативности за
  человеком»), а не ранжирует их сама — оценивает человек, глядя на экран.
- **Потолок API — 1.5, а не 2.0.** `--temperature 2` теперь отклоняется
  **локально**, до сети, с понятным сообщением вместо 422 от API — баг ехал
  с Day 01.
- **Гигиена замера**: штатная персона проекта («лаконичный ассистент, без
  воды») снимается на время развёртки — она прижимает длину и разнообразие,
  то есть ровно то, что день измеряет (тот же приём, что и в стратегиях
  Day 03). `top_p` обнуляется с предупреждением: Mistral рекомендует менять
  либо его, либо `temperature`, не оба сразу.

### Команда и флаги

```bash
uv run advent w01 temp                                    # три задачи, 0/0.7/1.2, 3 прогона
uv run advent w01 temp --problem alice                     # только одна задача
uv run advent w01 temp --temps 0,0.7,1.2,1.5                # добавить потолок API в развёртку
uv run advent w01 temp --runs 10                            # офлайн-sweep для отчёта
```

| Флаг | Значения | По умолчанию |
|------|----------|--------------|
| `--problem` | id задачи из `problems/`, `all` — все три задачи дня | `all` |
| `--temps` | температуры через запятую, потолок API 1.5 | `0,0.7,1.2` |
| `--runs` | прогонов на ячейку задача×температура | `3` |

Креативность open-задач (`coffee`) эта команда не оценивает сама — печатает
все ответы каждой температуры рядом (блок «оценка креативности за
человеком»), а балл ставит человек, глядя на экран. Прежний LLM-судья дня 04
(`--judge`/`--judge-model`, своя схема и промпт) убран целиком —
пользовательское решение. `--judge`/`--judge-model` остаются только у `solve`
(Day 03).

### Вывод дня: температура не про точность

Офлайн-sweep, 10 прогонов на ячейку, `mistral-small-latest`, той же командой
`advent w01 temp`, что идёт на видео:

| задача | t=0 | t=0.7 | t=1.2 |
|---|---|---|---|
| **`digits5`**, верно — модель по умолчанию **права** | **10/10** | 8/10 | 5/10 |
| **`alice`**, верно — модель по умолчанию **ошибается** | **0/10** | 2/10 | 5/10 |
| `digits5`, различных ответов | 5 из 10 | 10 из 10 | 10 из 10 |
| `alice`, различных ответов | 2 из 10 | 10 из 10 | 10 из 10 |
| `coffee`, различных ответов | 2 из 10 | 8 из 10 | 9 из 10 |
| соблюдение формата, все три задачи | 10/10 | 10/10 | 10/10 |

**Температура не повышает и не понижает точность. Она увеличивает разброс
вокруг того, что модель считает наиболее вероятным.**

- Модальный ответ верен (`digits5`) — разброс только портит: 10/10 → 5/10.
- Модальный ответ неверен (`alice`) — только разброс и даёт шанс: 0/10 → 5/10.
- При 1.2 обе задачи сходятся к 5/10: модель всё меньше опирается на своё
  «мнение» и всё больше на случай.

Поэтому «низкая температура = точность» — миф того же сорта, что «t=0 =
детерминированность». Низкая температура даёт не правильность, а
**повторяемость**: если модальный ответ неверен, она гарантирует, что он будет
неверен каждый раз. На `alice` при t=0 это ровно 0 из 10.

Отсюда же следует, что вопрос «какая температура точнее» некорректен без
указания задачи — и показать это можно только **парой**. `digits5` и `alice`
идут в развёртке вместе именно поэтому; поодиночке каждая даёт уверенное и
неверное обобщение.

### Для каких задач какая температура

| Температура | Когда уместна | На чём основано |
|---|---|---|
| **около 0** | задачи, где модель и так знает верный ответ, а нужна повторяемость: извлечение данных, форматирование, счёт по известному алгоритму | `digits5` 10/10 — лучший результат дня |
| **около 0.7** | компромисс по умолчанию: ответы уже не повторяются, но ещё и не разваливаются | `coffee` 8 из 10 различных при 10/10 формата |
| **1.2 и выше** | генерация вариантов, где нужен разброс, а не правильность: названия, черновики, брейнсторм; **а также задачи, где модель систематически ошибается** — там разброс единственный источник верного ответа | `coffee` 9 из 10 различных; `alice` 5/10 против 0/10 при t=0 |

Строка про «модель систематически ошибается» — не теория, а прямое следствие
колонки `alice`. Способ применения на практике: несколько прогонов при высокой
температуре плюс голосование, вместо одного прогона при нулевой.

### Три вещи, которые замер опроверг

- **Формат не разваливается от температуры.** 10/10 на всех трёх температурах
  у всех трёх задач. Развал, который наблюдался в предварительном замере,
  получен на формулировке «Ответь одной строкой» без «без пояснений и без
  вариантов». **Это свойство слабого промпта, а не высокой температуры.**
- **Разнообразие — не то же самое, что креативность.** Пока в дне был
  LLM-судья, он ставил `t=0.7` выше и `t=0`, и `t=1.2`, то есть ровно
  наоборот числу различных ответов; про ответ при 1.2 он написал «почти
  дублирует ответ A, теряя оригинальность из-за регистра букв». Судью потом
  убрали (оценка креативности — за человеком), но вывод остался: подставить
  число различных вместо оценки означало бы выдать одно за другое.
- **Единственная метрика, ведущая себя как обещано, — разнообразие.** Растёт
  монотонно на всех трёх задачах: 5→10→10, 2→10→10, 2→8→9.

### Что уже измерено (живой прогон против REST, до реализации команды)

Из `specs/SPEC-w01d04.md` §2 — сырые REST-замеры на `mistral-small-latest` и
`magistral-medium-latest`:

- **Потолок temperature у Mistral — 1.5, а не 2.0.** `t=1.5` → 200 OK,
  `t=1.51` и `t=2.0` → 422 (`"Input should be less than or equal to 1.5"`).
  Диапазон 0–2 — это OpenAI, у Mistral его нет.
- **`temperature=0` не детерминирован.** Один и тот же вопрос, 5 прогонов при
  `t=0` дают **2 разных ответа из 5**; с `random_seed=42` — тоже **2 из 5**.
  Seed при нуле не помогает не потому что сломан: при `t=0` декодирование
  жадное, шага sampling нет, seed применять некуда. Остаточное расхождение —
  порядок операций с плавающей точкой в параллельных вычислениях на сервере,
  свойство всех LLM API. Утверждение узкое: **t=0 не гарантирует одинаковый
  ответ**, а не «seed не работает вообще».
- **При 1.5 ломается не стиль, а токены.** Дословный пример из живого
  прогона — греческие и ивритские графемы посреди русского слова, склеенный
  латинский мусор:

  ```
  Давай предложу один вариант в видеπουργего лучика Средиземья
  "Морская Ароматка" → Морская АромакаפהMobJS
  ```

- **`default_model_temperature` — своё у каждой модели.** `0.3` у
  `mistral-small`, `mistral-large`, `ministral-8b`; `1.0` у
  `magistral-medium`. Незаданная температура — не 0 и не 1, а четвёртый
  режим, отдельный от всех трёх режимов задания.

## Настройки модели

Список моделей, их возможности и рекомендованные настройки берутся из живого
`GET /v1/models`, а не зашиты в код. По каждой модели API отдаёт `capabilities`,
`max_context_length` и `default_model_temperature` — на этом и построены команды.

**`/model list`** — таблица chat-моделей (29 из 48 на этом аккаунте):

```
┌─────────────────────────┬──────┬─────┬──────────────────────────┬─────────┐
│ id                      │  ctx │  t° │ возможности              │ алиасы  │
├─────────────────────────┼──────┼─────┼──────────────────────────┼─────────┤
│ codestral-2508          │ 250k │ 0.3 │ tools, fim               │ …       │
│ magistral-medium-latest │ 256k │ 1.0 │ reasoning, vision, tools │ …       │
└─────────────────────────┴──────┴─────┴──────────────────────────┴─────────┘
```

`/model list all` добавляет embedding, OCR и аудио-модели.

**`/model info`** — карточка текущей:

```
запрошена        mistral-small-latest
реальная версия  mistral-small-2603
описание         Mistral Small 4.
контекст         256k
рекоменд. t°     0.3
возможности      reasoning, vision, tools
алиасы           mistral-small-latest, mistral-vibe-cli-fast, magistral-small-latest
```

Модель, снимаемая с поддержки, помечается жёлтым и печатает дату вывода вместе
с заменой — узнать об этом лучше заранее, чем по внезапной ошибке.

**`/params` и `/set`** — крутить генерацию на лету:

```
/set temperature 0
/set reasoning_effort high
/set max_tokens default      # сбросить
```

Доступны `temperature`, `top_p`, `max_tokens`, `random_seed`, `stop`,
`reasoning_effort`. Те же значения задаются флагами CLI и переменными `.env`.

## Решения, которые стоит объяснить

- **SDK `mistralai` версии 2.** Импорты переехали из `mistralai` в
  `mistralai.client`; версия запинена в `pyproject.toml`, иначе примеры из
  интернета для v1 не заработают.
- **Незаданный параметр не отправляется вообще.** Соблазн подставить
  `temperature=0.7` константой велик, но API уже знает рекомендованное для
  каждой модели значение — у `mistral-small-2603` это 0.3, у `magistral-medium`
  1.0. Зашитая в клиент константа была бы хуже для половины моделей. Поэтому
  рекомендованное значение показывается в колонке `t°`, но подставляет его сервер.
- **Параметр, которого модель не умеет, отсеивается с предупреждением.**
  `reasoning_effort` есть у `mistral-small` (`reasoning: true`), но не у
  `codestral` (`reasoning: false`). Отправить его туда — получить либо молчаливое
  игнорирование, либо 422 посреди демо:

  ```
  $ advent w01 chat "Скажи ровно: два" --model codestral-latest --reasoning-effort high
  Два.
  codestral-latest не поддерживает: reasoning_effort — параметры не отправлены
  · model codestral-latest → codestral-2508  ·  1292 ms  ·  tokens 55/4/59
  ```

- **Стрим печатается сырым текстом**, без markdown-рендера. `rich.Live` с
  перерисовкой мигает на длинных ответах, жрёт CPU и ломается при редиректе
  в файл.
- **Реальная версия модели берётся из списка моделей.** API возвращает то же
  имя, что прислали, поэтому `-latest` пришлось бы показывать как есть — а
  через месяц было бы непонятно, чем именно записано видео.
- **Принудительный UTF-8 на потоках.** Консоль Windows по умолчанию отдаёт
  cp1251, и кириллица в ответе превращается в мусор прямо в кадре.
